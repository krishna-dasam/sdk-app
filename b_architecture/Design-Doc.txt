State Management Approach:

Client-Side State: The raw ArrayBuffer of the
currently opened PDF is held in memory (pdfBytes).
Viewer State: pdf.js maintains the rendering state (scale, current
page).
Edit State: A JavaScript Set (selectedPages) tracks which pages are
selected in the Document Editor mode. Document manipulations (rotate,
delete) are applied in memory using pdf-lib, replacing the active
pdfBytes.
Server-Side State: The server acts strictly as a stateless file
repository. Source-of-truth documents are persisted in the local file
system.


Key Tradeoffs Client-side vs Server-side Rendering: 

Processing edits and rendering entirely in the browser (via WebAssembly/JS) 
minimizes server compute costs and reduces latency for the user. The tradeoff is higher
memory usage on the client's browser, which could struggle with massive
(1GB+) PDFs.
Library Selection: pdf.js and pdf-lib were chosen to avoid restrictive
commercial SDK licensing while fulfilling all MVP requirements. While
highly capable, pdf-lib lacks native UI components, necessitating custom
grid and toolbar development compared to drop-in commercial
alternatives.
Linearization: pdf.js supports HTTP range requests for linearized PDFs
out-of-the-box, but the current Spring Boot controller serves the whole
file. Implementing HTTP 206 Partial Content is required for true fast
web view.
